# WB17-05 补修：训练取消时序与真实权重校验

日期：2026-11-05　分支：`workbuddy/haixun-v1.7.0`　基线：`88ec992`

来源：`项目资料/WorkBuddy开发与固定网址方案_20261104/` 的两条独立反例——
`verify_phase05_cancel_during_prepare.py`（证据 `WB17-05准备时取消竞态.json`）、
`verify_phase05_nonmodel_checkpoint.py`（证据 `WB17-05无模型PT独立核验.json`）。
本轮只修这两个根因，不动前端、MCP、命令分析与其它 CRUD。

## 1. 准备阶段取消后仍启动

**根因**：`start()` 建完 `queued` 行后还要做一轮很慢的准备（生成运行时 `data.yaml`、
vendor 数据解析器校验），最后才 `_spawn()`；`cancel()` 只看 `pid` 是否为空，就宣布
`cancelled` 并释放训练槽。两者之间没有共享的原子交接点，取消拦不住后面那次 spawn。

**改法**（迁移 **v17** 新增 `training_runs.launch_state`）：

| 阶段 | launch_state | 取消的行为 |
| --- | --- | --- |
| 准备中 | `preparing`（建行时写入） | 条件 UPDATE 原子抢行：赢的一方立刻写 `cancelled` 并放锁 |
| 启动交接 | `launching`（spawn 前认领） | **拒绝**：409 `CANCEL_STARTING`，不改状态、不放锁，等 PID 落库后重试 |
| 已登记 PID | `NULL` | 走原有“核身份 → 终止 → 核实”路径 |

- `_claim_launch` 与 `_claim_cancel_while_queued` 抢**同一行**（`status='queued'` +
  `launch_state`），靠 rowcount 决胜负；不是“spawn 前再 SELECT 一次”。
- 认领失败且行已终态 → `start()` 抛 409 `TRAINING_CANCELLED`，**一个进程都不起**。
- 进程起来后先 `_set_pid` 再 `_mark_running`，后者带 `WHERE status='queued'`：
  极端窗口里被取消的 run 不会被改回 `running`。

**PID 写库失败**：`_persist_pid` 先用新连接重试一次；仍失败则
`_terminate_tree` 终止并核实 → 标 `failed` 放锁；核实不了（`still_alive=True`）→
**保留训练槽**，把 `TRAINING_PID_UNRECORDED` + 真实 PID 写进可诊断状态（写不进就记日志）。

**`_terminate_tree` 只认明确证据**：只有 `NoSuchProcess` 算“已退出”；
`AccessDenied`（进程对象读不出来）、子进程枚举失败、`wait_procs` 失败分别返回
`PROCESS_UNREADABLE` / `CHILDREN_UNKNOWN` / `WAIT_FAILED`，一律按**仍存活**处理，
与 v1.6 `training_runner._process_alive`（AccessDenied 视为存活）的保守原则一致。

## 2. 只有 names 的 PT 被当成模型

**根因**：`inspect_weight` 只要能读出 `names` 就放行；`model` 缺失时把 `kind` 记成
`unknown` 依旧返回。`models.create_trained` 于是把它登记成“训练成功”的模型，
真到推理才炸。

**改法**：`inspect_weight` 要求 checkpoint 里真的有 `model` 或 `ema`，且必须是 vendor
`ultralytics.nn.tasks.BaseModel` 的子类（YOLO/YOLOMM 支持的架构）。空字典、只有
`names`、`model: None`、普通字典/数字等“非模型对象”、文本伪 PT 全部拒绝：

| 情形 | 错误码 |
| --- | --- |
| 没有 model/ema、或不是 BaseModel | `VISION_WEIGHT_NOT_MODEL` |
| 文本文件 / 结构不是 checkpoint | `VISION_WEIGHT_INVALID`（来自 `WEIGHT_UNVERIFIABLE`） |
| 未审核的反序列化符号 | `VISION_WEIGHT_UNTRUSTED`（不变） |

导入、训练产物登记都走这个函数；**发布**新增 `_verify_publishable_weight()`，
复用同一套校验并比对登记时的类别表，返回 `MODEL_WEIGHT_MISSING` /
`MODEL_WEIGHT_INVALID` / `MODEL_WEIGHT_CHANGED`。EMA-only（`model=None, ema=模型`）
的训练态权重仍然接受。

## 6. 补充轮（2026-11-06）：独立复核提出的三条分支

来源：`WB17-05-取消权重独立复核补充.md` 与三份证据
（`WB17-05进程收尾独立契约.json`、`WB17-05未登记PID恢复独立核验.json`、
`WB17-05真实权重结构独立核验.json`）。只改这三条直接相关的分支，未动 UI / MCP / 其它 CRUD。

### 6.1 根进程退出 ≠ 整棵树结束

**现象**：`_terminate_tree` 在 `root.terminate()` 抛 `NoSuchProcess` 时直接返回
`(False, ALREADY_GONE)`，把已经枚举到的 children 整个跳过；训练 worker 通常会再拉子进程，
于是“根没了”被误报成“整棵树结束了”。

**改法**：根进程消失后仍对**已枚举**的 children 走 wait → kill → 再 wait 并核实；
只要还有存活或核实不了就返回 `(True, KILL_TIMEOUT)`。分支收敛为：

| 情形 | 返回 |
| --- | --- |
| 根进程取对象时就消失（还没枚举过树） | `(True, PROCESS_VANISHED)` |
| `children()` 抛错 / 枚举中根消失 | `(True, CHILDREN_UNKNOWN)` |
| 根没了，但已枚举的子进程仍存活 | `(True, KILL_TIMEOUT)` |
| 根没了，已枚举的子进程都退出 | `(False, TERMINATED)` |
| 根没了，且当时一个子进程都没枚举到 | `(False, ALREADY_GONE)` |

### 6.2 未知启动交接不能因重启被放锁

**现象**：`recover()` 看到 `pid=null` 就按“没有结果”标 `interrupted` 并放锁——把一个
可能还在跑的 worker 说成结束，还让下一次训练能立刻抢到槽位。

**改法**：`pid` 为空且 `launch_state='launching'` 时走新分支 `_mark_launch_unknown()`：
只写 `TRAINING_PROCESS_UNKNOWN` 诊断，**不改状态、不放锁**，统计里记 `runs_blocked`。
随后第二次训练仍被 `TRAINING_BUSY` 拒绝，也不会自动重跑。

同步核对过的同类路径：

- `cancel`：`launching` + 无 PID 时仍只返回 409 `CANCEL_STARTING`；提示补充了
  “若服务刚重启过，说明 PID 从未落库，需要人工核对”。
- `get` / `list`：只读，不推断状态。
- `_finalize` / `_mark_terminal`：只在有真实结果或已确认退出时调用。

**代价（有意为之）**：这是需要人工介入才能解除的保守阻塞。若进程其实早已退出而证据缺失，
训练槽会一直占用——宁可阻塞，也不把未知当结束；解除方式仍是人工核对进程后处理。

### 6.3 模型选择必须与 vendor 的 EMA 优先一致

**现象**：`_checkpoint_model` 写的是 `model` 优先，注释还声称“与 vendor 一致”，但 vendor
`nn/tasks.py` 实际是 `(ckpt.get('ema') or ckpt['model'])`。两个键同时非空时，
导入检查与实际运行选了不同对象。

**改法**：改成 `checkpoint.get("ema") or checkpoint.get("model")`，注释与错误信息同步。
反向组合（`model` 合法、`ema` 是普通模块）同样拒绝——不能“检查 model 通过、真跑用坏 ema”。
vendor 加载行为一行未改。

### 6.5 本轮之后仍存在的限制

- `PROCESS_VANISHED` / `CHILDREN_UNKNOWN` 会让取消返回 409 `CANCEL_FAILED` 并保留槽位，
  由 watcher 在进程真正退出后 `_finalize` 收尾；极端情况仍需人工确认。
- 未知启动交接没有“强制清除”入口：解除依赖人工核对进程（未做进程扫描框架）。
- 未跑真实训练；MCP 的 `NoEventLoopError` 仍按待办保留，本轮未混改。
