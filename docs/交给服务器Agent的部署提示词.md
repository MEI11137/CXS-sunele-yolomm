## 固定目标

- 保留当前发布地址：`https://haixun-inspection.app.workbuddy.host/?sharecode=YHJNHOFRKT`。
- 当前实现：WorkBuddy 云端托管现有前端和同源网关，本机 `connector.js` 主动连云端，再访问 `http://127.0.0.1:8080`。服务器不必登录 WorkBuddy；更新线上页面时才需要原发布账号更新原应用。
- 候选源码仓库：`https://github.com/MEI11137/CXS-sunele-yolomm.git`，分支 `workbuddy/haixun-v1.7.0`。先实际验证分支和记录 SHA；若网络失败或缺少未发布修订，明确报告，不能擅自用旧版替代后声称最新版已部署。
- 网关与连接器**已经整合进主仓库**：`deploy/workbuddy/server.js`、`deploy/workbuddy/connector.js`、`deploy/workbuddy/prepare.mjs`、`deploy/workbuddy/preflight.mjs`，启动器是根目录 `启动WorkBuddy云端连接.cmd`。`git clone` 之后这些都应当存在，先核对 SHA 与文件齐备，再继续。
- 仍然**不会**由 Git 提供两样东西，这是有意设计：① 与云端配套的 `.tunnel-token`（私密传到 `deploy/workbuddy/.tunnel-token`，不重生成、不上传）；② `web/`（在 `frontend` 里 `npm ci && npm run build`，再 `node deploy\workbuddy\prepare.mjs` 生成）。只跑后端 + 连接器时不需要 `web/`。

## 先盘点，再配置

1. 只读检查已有代码、端口、进程、服务、数据目录、账号、工作目录、Python/Node/OpenCode/GPU 版本；识别现有实例，不杀陌生进程，不重复打开同一数据库。
2. 已有部署保留本机自己的账号、数据库、密钥、模型 API 配置和业务数据。先备份，不拿开发机的测试库或 secrets 覆盖。
3. 建立明确的代码目录、私有运行目录、业务工作区和连接器目录；私有数据区不能授权给评委浏览。
4. 使用项目独立 Python 环境，不覆盖本机原有 YOLO/torch 环境。当前引擎闸门是 OpenCode 1.19.4，不关闭版本检查、不启用假引擎。Node 建议 22.6+（≥18 是硬要求）：它用于构建前端和运行 WorkBuddy 连接器，**后端服务本身不需要 Node**。
5. 所有 CLI 建号、目录授权、服务启动使用同一 `HX17_DATA_DIR`。已有账号不重置；首次部署才通过本机安全交互创建管理员/普通评委账号。
6. 模型连接使用本机所有者提供的 API Key、真实模型 ID 和 API 地址；按网站用户配置，不把管理员配置或另一台电脑的配置当作普通账号的配置。秘密不得出现在聊天、命令历史、Git、公网页面或报告中。

## 执行要求

- 安装依赖、构建当前前端、以 Waitress 同源启动后端，绑定 `127.0.0.1`，默认 8080。端口变化同步调整连接器和自有域名 Tunnel。只有需要重新发布 WorkBuddy 云端页面时才执行 `node deploy\workbuddy\prepare.mjs` 生成 `web/` 并上传整目录；仅仅是让现有云端入口转到本机，只需要 `connector.js` + `.tunnel-token`。
- 先在本机验证后端和个人模型连接，再切换公网。切换前明确停旧电脑连接器，再启本机连接器；不能两台连接不同数据库的机器同时连同一入口。
- 仅授权实际评委账号操作约定工作文件夹，保留手工上传和页面操作。普通账号不能看到未授权目录或他人项目。
- 保留 Cookie、HTTPS、CSRF、Origin 与项目归属检查；不通过通配 CORS、关闭 CSRF、伪造任意 Origin 让验收“通过”。`/api/service/**` 不能对公网开放。
- `.tunnel-token` 只是 WorkBuddy 反向通道凭据，不是模型 API Key，也不是 Cloudflare 凭据。只检查本机配置是否匹配，不随机重生成，不上传仓库。
- 当前连接器 `--check` 的退出码不能作为全部成功依据；必须真实打开公网链接、普通账号登录并发起业务请求。
- 自有域名审核完成后，按指南核对 DNS、NS、正式 Tunnel、HTTPS、Host 转发与 `/api`；保留已有邮箱/网站记录，不整区清空。不凭空填写域名、UUID 或凭据。
- 有可复用的正式 Tunnel 时先审查并复用；核对学校允许的出站连接，Cloudflare Tunnel 特别检查出站 7844。不要把内网 IP 写进公网 A 记录，不改用直连方案或擅自购买云服务器。保留 WorkBuddy 原入口，与自有域名并行访问同一个本机后端。
- 所有产生的数据集、标签、权重和训练产物落在约定业务工作区；数据库和密钥留私有运行目录。源数据与运行态分开备份。
- 安装、构建或检查失败先处理真实根因。若涉及产品代码修改，保留最小差异并做针对性验证，不能用空返回或模拟结果掩盖失败。

## 必须实际验收

1. 本机健康与版本、GPU/视觉依赖、OpenCode 引擎是否真实可用。
2. WorkBuddy 原链接保持不变；用新服务器独有的账号/项目标记证明公网请求确实到了本机。
3. 普通评委账号的登录、新建项目、目录授权与绑定、数据集/权重的手工入口、页面刷新。
4. 内嵌 Agent 真正调用查询工具，给出最终回答；刷新后回答仍在。不要把“工具成功”当作“对话完成”。
5. 图像与文件预览、下载、CSV、双模态复核编辑；图像坐标与文件来源可追溯。
6. 付费 API 仅在已授权范围内使用；小批量检测/AI 核查按明确样本与置信度验证，不擅自扩大。训练只有明确授权后进行，检查真实进程和产物。
7. 未登录、越权、伪造 Origin、缺 CSRF、管理路由、断线与恢复的拒绝/提示行为。
8. 自有域名未审核时写“待完成”；审核后在外部网络真实验收该入口。一次页面 200 不等于业务验收完成。

验证成功后，再按用户授权设置后台常驻/自动启动，使用正确 Windows 用户、绝对路径、固定工作目录、同一数据目录和去敏日志。不要覆盖别的项目的计划任务或服务。

目前已授权的范围内持续执行；只有确实缺少必须的信息、凭据输入或所有者操作时，才明确说明阻塞点。不要让用户反复批准已经授权的普通配置步骤，也不要替用户决定购买、升级或重置已有账号。
