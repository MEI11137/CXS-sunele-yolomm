## 2. 结构变更

### 2.1 数据库（迁移 v7，仅前向）

- v6：`assets` / `datasets` / `dataset_samples` / `models` / `detections` / `ai_reviews` / `jobs` / `job_events`。
- v7：`turns.attachment_ids`（本轮附件资产 ID，JSON 数组）。
  **为什么放 turns 不放消息 meta**：运行器发起 prompt 前必须拿到「这一轮带了哪几张图」，
  且附件归属要跟轮次一起可审计；消息 meta 会被后续刷新覆盖，不适合做执行依据。

### 2.2 错误模型

- `ToolError` 新增 `details`（结构化、非敏感，例如 `NEED_CLASS_MAPPING` 的两份类别清单），
  没内容时不出现在输出里，原有错误格式不变。
- 新增 `tools._service()`：把业务层 `ApiError` 翻成工具层 `ToolError`，保留机器码、中文说明与 details。
  之前业务服务抛 `ApiError` 会穿透网关的 `except ToolError`，表现为 500 + `tool_jobs` 卡在 running。

### 2.3 模型来源统一（本轮修掉的真实分裂）

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| `gateway.actor_for()` | `connection.provider/model` | `turn.provider/model`（连接值仅作旧数据兜底） |
| `identity.resolve()` | 只按偏好解析 | 新增 `model=` 显式快照；视觉证据按该模型重新判定 |
| `aireview.start_batch()` | 按偏好解析 | 接受 `model` 快照，存进作业 payload |
| `aireview._review_one()` | 每次按偏好重解析 | 用作业里的快照，中途切模型不影响已排队作业 |
| `pipelines.start_inspection()` | 无模型快照 | payload 里带 `review_model`，核查阶段沿用 |

后果对照：偏好设 B、连接仍是 A 时，之前是「聊天用 B、核查用 A」，而视觉证据只对 A 成立；
现在两侧都用 B，且 B 没有证据就直接 `VISION_UNVERIFIED`，不会退回 A。

### 2.4 引擎失效范围（用户点名的缺陷）

- `runner._poll` 连续读失败：从 `manager.stop_project()` 改为 `manager.quarantine(instance)`。
  一个会话的引擎读不出来，不再顺手杀掉同项目其它会话的引擎。
- 新增 `PROJECT_SCOPE_CODES = {PROJECT_CLOSED, GRANT_REVOKED, NO_PROJECT_ROOT}` 与
  `manager.quarantine_project()`：只有项目级失效才作用于整个项目（存储一律保留，撤权恢复后历史还在）。

## 3. 关键设计与取舍

1. **类型判定按内容不按扩展名**：`sniff()` 先 PIL 验证像素，再判断 zip 内是否有 `data.pkl`；
   图片 `kind=image`（不是 `project_file`），ZIP 里有 pickle 判为 `weight`。
2. **原图永不改写**：检测结果画在 `artifacts/<record>/result.jpg` 上，`image_rel` 始终指向原图；
   测试用「检测后再取内容流，字节相等」验证。
3. **模态不许顶替**：非 edge 模态缺配图直接 `VISION_X_REQUIRED`/`MISSING_MODALITY`；
   edge 允许派生但记 `x_origin=derived`，页面上也照实显示。
4. **幂等靠 `request_key`**：单图检测、批检测、核查、巡检都带键；重复提交返回同一条记录/同一个作业。
5. **失败要看得见**：缺权重在建记录**之前**报 `MODEL_WEIGHT_MISSING`（不留 running 孤儿）；
   核查失败写 `status=failed` + `error_code`，`verdict` 保持 NULL。
6. **长任务与对话解耦**：业务事件按 session 拉，游标是 `job_events.seq`；
   对话轮次结束、刷新页面、切到业务页都不会丢进度。
7. **附件是真图**：`runner._attachments()` 读真实字节 → base64 data URI → `{type:'file', mime, filename, url}`；
   只给路径不算「带图」。发图前要求 `verified_vision(conn, uid, turn.model)`。
8. **`full` 模式不弹卡**：业务工具风险等级为 read/write，`full` 下自动执行并审计，不产生计划卡或逐图确认卡。

## 7. 已知缺口（不掩饰）

1. **附件 part 的引擎侧兼容性未用真实模型验证**：结构按 OpenCode 1.19.4 的 file part
   （`{type:'file', mime, filename, url}`）实现，回环假引擎验证了「发出去的是真实字节」；
   真实模型侧要等有可用的视觉连接时再确认一次。**没有**付费调用，所以不宣称「已端到端通过」。
2. **巡检的「接力」只做到事件层**：长任务完成后业务卡片会自己出现（会话级轮询），
   但不会自动往对话里追加一条模型发言——那会产生未经用户同意的新一轮（可能计费）。
   页面上给的是明确的下一步入口（记录页/详情），符合「不偷偷再跑一轮」的边界。
3. **人工复核与回流未实现**，因此「完整闭环」只在检测→核查→队列这一段成立；
   `features` 与工具清单都保持未实现状态，界面不显示假按钮。
4. **巡检上限与并发**：`MAX_BATCH=50`、线程池 2；一次几千张会排队较久，界面上有进度但还没有取消作业的入口。
5. **`frontend` 业务页未做移动端适配**：宽表格在窄屏会横向滚动，尚未折叠成卡片列表。
6. **旧格式（非 zip）`.pt` 现在会被拒绝**：安全加载需要静态解释 `data.pkl` 才能给出许可判定，
   旧格式没有 `data.pkl`。理由是「不能为了兼容而放弃检查」，如果以后确实遇到旧版权重，
   应先离线转存为 zip 格式再导入。

### 9.1 越界校验晚于写入

- **现象**：`root/uploads` 被换成指向项目外的 NTFS 联接后，`assets.add_bytes` 最终报
  `ApiError`，但 `outside/image/outside-write.png` 已经写出。
- **原因**：`storage.project_dir()` 先 `mkdir`、`unique_path()` 再 `exists()`，
  越界判断发生在 `relative()`，属于**事后**检查。字符串上 `uploads/x.png` 在项目内，
  真实落点却在外面。
- **改法（`backend/services/storage.py` 重写为唯一写盘入口）**：
  - `guard(root, target)`：`realpath` 解析后判「仍在项目内」且「不落私有区」；
  - `project_dir()`：**先 guard → mkdir → 再 guard**，联接在创建之前就被拒；
  - `write_stream()/write_bytes()/copy_into()`：临时文件 → 校验 → 原子替换，失败清理只删受控目录里的临时文件；
  - `remove_tree()`：失败清理前同样过 guard，拒绝删项目根或项目外目录；
  - 私有区判定抽到 `backend/paths.py`（`configure_private/is_private`），
    `fsops` 与业务文件服务共用同一份规则，不再各写一套；应用工厂启动时就登记 `data_dir`/`secrets`，
    不依赖「先起过一次 Agent 网关」。
- **证据**：脚本 `junction_rejected_before_any_outside_write = true`；
  仓内回归 `test_junction_escape_is_rejected_before_writing_outside`。

### 9.2 同名并发上传互相覆盖

- **现象**：两个线程同时上传不同颜色的 `pair.png`，两条资产共用 `rel_path`，
  实际只剩一份字节，一条 SHA 校验失败。
- **原因**：`unique_path()` 的「查一次不存在」不是原子操作，两个线程都看到「不存在」后拿到同一路径。
- **改法**：资产按 **asset id 分目录**——`uploads/<kind>/<asset_id>/<原文件名>`。
  路径在生成时就唯一，不依赖检查与写入之间的时间差；原文件名与原字节仍可追溯。
  `unique_path()` 降级为「只取名，不建目录」，目录必须先经 `project_dir()` 校验。
- **证据**：`concurrent_uploads_use_distinct_paths = true`、`concurrent_uploads_preserve_both_inputs = true`；
  仓内回归 `test_same_name_concurrent_uploads_keep_both_files`（用 Barrier 强制两个线程同时拿到候选名）。

### 9.3 时间相同的分页漏项

- **现象**：两条资产 `created_at` 相同，`limit=1` 翻第二页时丢掉一条。
- **原因**：排序是 `created_at DESC, id DESC`，游标却只有 `created_at`（`created_at < ?`），
  同时间的另一条被整体跳过。
- **改法**：`assets.list_for_project` 的 `before` 改为**资产 ID**，服务端取回该行的
  `(created_at, id)` 再按 `(created_at < ? OR (created_at = ? AND id < ?))` 过滤；
  `next_before` 返回 ID。与 `detections`、`sessions` 的分页语义保持一致（UI/工具都是不透明游标）。
- **证据**：`timestamp_tie_pagination_complete = true`；
  仓内回归 `test_pagination_with_identical_timestamps_does_not_lose_rows`。

### 9.4 PT 在验证前执行任意 pickle

- **现象**：`runtime.inspect_weight()` 直接 `torch.load(weights_only=False)`；一个把
  `Path.write_text` 塞进 `__reduce__` 的探针权重，虽然后来被判「非法模型」，哨兵文件已经写出。
- **原因**：反序列化本身就是执行。先执行、后验证的顺序不成立；
  同一 Windows 账号的子进程也不构成沙箱。
- **改法（新增 `backend/vision/safe_weight.py`）**：两道关，缺一不可。
  1. **静态解释**：只读 zip 里的 `data.pkl`，用 `pickletools.genops` 取出所有
     `GLOBAL`/`STACK_GLOBAL`，不执行字节码；
  2. **执行闸门**：真正加载时用带同一判定的 `Unpickler.find_class`，
     扫描之后文件被替换也拦得住。
  许可策略是白名单且**只认类型**：`torch.nn.Module`/`torch.Tensor` 子类、torch legacy storage、
  `torch.Size`、`ultralytics.` 下的 `nn.Module` 子类，外加显式点名的纯数据类型
  （`OrderedDict`、`set`、`pathlib.WindowsPath`、`MultiModalRouter` 等）与固定几个张量重建函数
  （`_rebuild_tensor_v2` 等）。**函数对象一律不放行**，也不做「载荷要什么就给什么」的自动放行。
  - `inspect_weight()` 改走 `safe_weight.load()`；
  - `activate_vendor()` 在进程内包装一次 `torch.load`：只有显式 `weights_only=False`
    （即会执行 pickle）的调用被接管，`weights_only=True` 原样放行。
    vendor 的推理加载因此也过同一道闸，**没有修改 vendor 源码**。
  - 非 zip 结构的旧格式权重直接拒绝（无法静态解释，不为兼容放弃检查）。
- **证据**：`untrusted_weight_rejected_without_executing_pickle = true`；
  仓内回归 `test_untrusted_weight_is_rejected_without_running_pickle`（同时验证
  `torch.load(weights_only=False)` 这条推理入口被拦）；
  **正向兼容**：真实 `best.pt` 经 `inspect_weight` 得到
  `[{0, single_hotspot}, {1, large_area_hotspot}]`，`YOLOMM` CPU 推理返回
  `[292.099, 630.293, 321.775, 649.496] conf=0.811741`，与审查前的验收结果一致。
  静态扫描显示该权重引用 25 个 globals，其中 10 个是 ultralytics 类、9 个 torch 类型、
  `pathlib.WindowsPath` 1 个、`_rebuild_*` 2 个、容器/存储若干——全部在白名单内。

### 10.4 权重加载改用 PyTorch 原生受限机制（删掉自制的 300 行）

- 事实核对：本机 `torch 2.13.0+cu126`；可信 `best.pt` 声明 **17 个** globals，
  在 `torch.serialization.safe_globals([...])` + `torch.load(weights_only=True)` 下**原生加载成功**，
  `names` 仍是两个真实热斑类别。
- 因此 `backend/vision/safe_weight.py` 重写为原生方案：
  `get_unsafe_globals_in_checkpoint()` 只读列出声明 → 逐个按**代码里的白名单**判定
  （`nn.Module`/`Tensor` 子类 + 少量纯数据类型）→ 任一不合规就拒绝、不加载 →
  通过后放进 `safe_globals` 用原生 `weights_only=True` 加载。
  删除了 `pickletools` 静态解释器与自制 `Unpickler`。
- 明确不放行 `torch.storage._load_from_bytes`（以及 `torch.load/save`、`eval/exec` 等间接入口）；
  函数对象一律拒绝（`pathlib.Path.write_text` 哨兵仍被拒）。
- 没有“安全失败就退回任意 pickle”的分支。`safe_globals` 是进程级状态，加载用模块级锁串行化。
- vendor 推理加载：`install_guard()` 只接管显式 `weights_only=False` 的 `torch.load`
  （`weights_only=True`/未指定的调用原样放行，带 `pickle_module` 的调用也放行），
  重定向到同一原生方案；未改 vendor 源码。
- 正向兼容：真实 `best.pt` 经 `inspect_weight` 得 2 类；`YOLOMM` CPU 推理
  `[292.099, 630.293, 321.775, 649.496] conf=0.811741`，与上一轮一致。

### 10.5 AI 核查的图片说明：模态不是来源

- 旧文案把 `x_origin`（uploaded/derived）当配图说明，模型可能把派生边缘图当红外解释。
- 现在 `_review_images` 按**资产角色**生成说明：`rgb → 可见光 RGB`、`ir → 红外 IR 热成像`、
  `edge → 边缘图（由 RGB 派生，不是真实红外）`、`x → 配套模态图（未标注）`，
  并附来源（上传/项目内文件/派生自哪个父资产）。
- 系统提示明确要求：派生边缘图不能当热成像判断温度；缺真实红外时不要假装看过红外。

### 10.6 作业完成后的结果与接力

- **不再把“轮次结束”当成“业务结束”**：作业终态时服务端用真实结果生成
  `job.summary` 事件（如「AI 核查完成：成功 2/2 条、失败 0 条」），
  会话级轮询把它显示在默认折叠的业务卡片里——不需要用户再发“你好”，也不需要再调一次模型。
- **同一目标内的后续步骤在本轮内继续**：系统提示与 `hx_job_status` 说明改为
  「每次 ≤10 秒、可连续调用做有界等待；拿到真实结果后继续执行已授权的下一步」，
  检测→核查、核查→定位复核页都在同一轮里真实执行，不再要求用户重新批准计划。
- 明确没有做：**不会**在轮次结束后自动另起一轮模型调用。那会产生用户没批准的新请求
  （可能计费），也等于第二套规划器；结果通知由服务端摘要承担。这一点写进了提示词。
