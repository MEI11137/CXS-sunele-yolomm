## 5. 独立审查后的补修（2026-11-06 第二轮）

Codex 在 5887 真实站点查看最新构建（`UI-v17-ui02-review-{light,dark}.png`），确认重复标题与整页边框已去；
后台对话回归 25 项由 Codex 独立跑过。本轮补两处：

### 5.1 `.sr-only` 缺失

`AssistantPanel` 用 `span.sr-only` 给权限/模型下拉做读屏标签，但全局 CSS 里没有这个类，
结果“权限模式”“模型”当普通文字显示出来，挤占输入框。已在 `styles.css` 补标准视觉隐藏样式
（1×1、`position:absolute`、`clip`），label 与 aria 未删，读屏名称仍是“权限模式”“模型”。

实测：两个下拉的 label 文本仍是“权限模式 / 模型”，`.sr-only` 盒为 1×1、`position:absolute`。

### 5.2 第一条消息就能带图片

原来附件按钮 `!sessionId` 直接禁用、粘贴/拖拽还提示“先发一条文字”，与普通 Agent 交互不符。
上传接口本就按**项目**存资产、`session_id` 可选，因此改为：

- 只要有当前项目就能选图；上传时 `sessionId: sessionId || undefined`；
- 选图**不建会话**，真正发送时由 `ensureSession()` 建第一条并提交资源引用；
- 换项目自动清空附件（不跨项目复用），失败保留草稿+错误提示，可重试；
- 占位文字改回“拖入图片”，本轮不开放 ZIP/PT/PDF 聊天附件（需后端非图片上下文契约）。

实测（隔离账号 `ui01`，新建项目绑定 `E:/智能体创新应用大赛/ui02-workspace/proj`）：
选一张真实 JPG → 出现 1 个附件 chip、无错误、URL 仍是 `/projects/:id`（**未建会话**）。
另测：未绑目录的项目选图 → 后端 409/403 原话显示在输入框内、草稿不丢；错放的 `var/` 目录被
存储守卫拒绝（403“指向服务端私有数据”），属于既有权限规则，未绕过。

### 5.3 未测

  本机无连接、不调付费接口，故只验证到“选图成功且不建会话”；发送建单条会话需协作者用真实上游复测。

## 6. 真实页面验收发现的四个缺口（2026-11-06 第三轮）

来源：Codex 的独立探针 `verify_ui02_chat.py`（普通 member + 真实页面 + 真实 OpenCode 1.19.4
+ 私有 MCP 文件工具 + 真实数据库，只有模型上游是本机慢速 SSE 桩），证据
`UI-02独立真实对话核验_首轮失败.json`、`UI-02独立真实对话核验.json`。
本轮只改对话与必要的公共消息逻辑，未恢复计划卡、未改权限、未动 5885/5886/5887 参考实例。

### 6.1 收尾时上翻被抢滚动

**根因**：`poll` 先写终态 → `showLive` 立刻变假（实时区整块消失）→ 内容高度骤降、视口被顶到
“看起来贴底”的位置 → `scroll` 事件把 `stuck` 改回 `true` → 落库消息到达后 `toLatest()` 把它拉到底。

**改法**（`ChatTimeline.vue`）：
- **交接期间不塌陷**：终态且正文还没落库时，实时区继续显示（只把忙碌点改成静态点），
  等 `meta.turn_id` 对应的落库消息到达才切换；始终不出现两份正文。
- **跟随状态只由真实手势改变**：滚轮/按键/指针按下才算“用户想滚”；`scroll` 事件若没有手势，
  即使算出“贴底”也不恢复跟随——布局变短造成的贴底不再被误读成用户意图。
- **暂停时锚定位置**：内容变化后把 `scrollTop` 还原到暂停时记下的位置；在顶部插入更早的消息
  （加载更早）时按新增高度补偿，视觉上仍停在原来那句话。
- **可恢复提示**：终态 1.5s 后正文还没读到，显示“回答已经生成，正在从服务端读取…”+「重新读取」。
- 「回到最新」在长距离时改为立即到位（原来几千像素的平滑动画又慢、探针 450ms 内也测不到底）。

### 6.2 发出的图片在历史里消失

**根因**：`routes/agent.py` 在补 `turn_id` 时 `UPDATE messages SET meta = ?` 整体覆盖，
把刚写进去的 `asset_ids` 丢了；前端也从未渲染消息附件。

**改法**：
- 后端改为**合并** meta（`dict(message["meta"])` 再 `update`），`asset_ids`/`source`/`request_id` 全保留。
- `ChatTimeline` 渲染 `meta.asset_ids` 的紧凑缩略图（84px），点击新窗口看原图；
  地址一律走已鉴权的 `/api/projects/{pid}/assets/{aid}/content`，不信任任何前端路径；
  加载失败（损坏/已删/跨账号 404）显示“图片不可用”占位。
- 已知边界：图片以**资产引用**存在消息 meta 里，正文永远不写 data URI 或密钥。

### 6.3 成功轮次的工具详情被整体移除

**根因**：`showRoundDetail` 只在「终态且未落库」时成立；成功轮有落库回答，工具记录就彻底消失了。

**改法**：每条含 `meta.turn_id` 且 `meta.tool_calls > 0` 的助手消息下面，默认收起一行
**“已完成 · N 项操作 / 查看执行详情”**；展开时才按该 turn 拉 `/turns/{id}` 事件并渲染工具明细。
历史每一轮的详情与**自己的 turn_id** 绑定，不会把最新事件挂到旧回答上；数据仍走鉴权接口。

### 6.4 真流式增量

**根因**：`/session/{id}/message` 的 text part 往往在整段输出结束后才完整落库，只轮询就是“最后一次性出现”。

**改法**（`engine.py` + `runner.py`）：
- `EngineManager.open_events()` 订阅 `GET /event`（SSE，基础认证同其它请求），`iter_events()` 解析 `data:` 行。
- `runner._live_loop` 把增量合并成**稳定 part_id 快照**写入 turn 事件（`text` + `live: true`），
  最多 120ms 一条；节流时**不写状态**，尾巴交给下一次快照或轮询。
- **安全过滤**（实测踩到）：1.19.4 的 `message.part.delta` 只有 `messageID/partID/field/delta`，
  **reasoning part 的 `field` 也是 `text`**——只看 field 会把内部思维链当正文上屏（第一轮探针正是这样
  失败的）。现在只有被 `message.part.updated` 明确标成 `type=text` 的 part 才放行，类型未知的增量
  先缓存不展示；`summary`/`synthetic`/`ignored` 与所有非 text part 一律丢弃。
- `_LiveText` 让事件流与轮询共享同一份状态：**只向前推进**，短快照不会把已显示的正文改短。
- 轮询仍是唯一的完成判定；订阅失败只损失实时性（探针里 fake 引擎 `/event` 404 就是这么走的）。
  终态/停止/异常都 `close()` 连接并 join 线程，不留悬挂线程。

## 7. 独立审查补修：增量边界与首发幂等（2026-11-06 第四轮）

### 7.1 增量的类型/会话边界（`backend/agent/runner.py::_live_loop`）

上一轮已按 part 类型拦住 reasoning/synthetic/ignored，但**没有校验 sessionID**，
也没有排除基线里的旧消息；而且被拒的 part 可能被后面一次不带 flag 的元数据刷新“洗白”。

现在的判定顺序（缺一条都不发文字）：

1. `sessionID` 与本次 `engine_session` 一致——`message.updated` 的 `properties` 与 `info`、
   `part.sessionID`、`delta.sessionID` 四处都查；
2. `messageID` 不在发起前取得的基线集合里（上一轮的回答不能算本轮）；
3. 消息是 `assistant` 且非 `summary`；非 assistant / summary / 基线旧消息一进拒绝集合就永不放行；
4. part 被 `message.part.updated` 明确标成 `type=text`，且不带 `synthetic`/`ignored`；
   reasoning / tool / step-* 一律永久拒绝——**后续 `field='text'` 的增量照样丢弃**；
5. 已拒绝的 part 即使再来一次“不带 flag、带正文”的快照也不会复活（这条由新单测抓到并修掉）；
6. 角色/类型未确认时增量只进**有界缓存**（单 part ≤4000 字符、最多 64 个 part），
   确认后再补发；正文统一按 `MAX_ASSISTANT_CHARS` 截断。

**订阅握手**：`_start_live()` 先启动线程并 `ready.wait(6s)`，等连接真正建立（或明确失败）才返回，
之后才 `prompt_async`；等不到就记一条 warning 并继续用轮询，不伪造流式。
`_LiveStream.close()` 先 `response.close()` 再 `join(2s)`——关连接会让阻塞的 `iter_lines` 立刻返回，
不会把“关掉一个 600 秒读超时的连接”当成停止。

**给协作者的入口说明**：`LiveStreamTest._run_live(frames)` 的签名没变，探针不需要改；
内部 `_live_loop(turn, instance, engine_session, live, stop, holder, baseline=None)` 只多了第 7 个
可选参数（基线 messageID 集合），`_start_live(..., baseline)` 多一个可选位置参数。

### 7.2 首条消息重复发送（`frontend/src/components/AssistantPanel.vue`）

**根因**：`send()` 里的校验都在第一个 `await` 之前完成，同一帧的两次点击各自通过，
`ensureSession()` 于是建了两条会话；`agent.sending` 要到 `agent.send` 里才置位，已经太晚。

**改法**：组件级 `sendingDraft` 覆盖整个“确保会话 → 发送”流程，按钮与 Enter 走同一把锁；
`canSend` 一并带上它（发送中按钮禁用）；`finally` 里必定释放，失败时草稿与附件原样保留；
附件 ID 在等待前快照，等待期间改附件不影响已发出的那条。服务端 `request_id` 幂等不动。
