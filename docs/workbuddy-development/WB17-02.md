## 2. 运行时架构

```text
浏览器 ──HTTP/Cookie+CSRF──▶ Flask 站点 (:5080/8080)
                                │
                                ├─ turns / turn_events / actions / tool_jobs (SQLite WAL)
                                │
                                ├─ TurnRunner（后台线程，每会话单活动轮次）
                                │     └─ EngineManager ──子进程──▶ opencode serve (:随机回环端口)
                                │                                   │
                                │                                   └─ stdio MCP 桥（子进程）
                                │                                          │ HTTP + X-HX17-Tool-Token
                                └─ ToolGateway（独立回环监听器，随机端口）◀─┘
                                        └─ tools → fsops / 项目 / 会话 / 跳转 / 提问
```

关键点：

- **网关端口不是站点端口**，不吃站点 Cookie，只在 `127.0.0.1` 监听；每次调用带 32 字节随机令牌，
  令牌绑定 `(user, project, session, turn, mode, 连接指纹)`，工具参数里没有 `user_id`，模型无法冒充他人；
- **每个「用户 + 项目 + 连接指纹」一个引擎实例**，运行目录在 `var/engines/<hash>/`，
  XDG（CONFIG/CACHE/DATA/STATE）+ HOME/USERPROFILE + TEMP/TMP/TMPDIR 全部指向该目录，
  启动前 `env -u NODE_OPTIONS`，因此不会读写全局 `~/.config/opencode`，也不读全局认证；
- 换个人连接（指纹变化）时旧引擎立即销毁并重建，旧轮次直接失败 `CONNECTION_CHANGED`；
- 引擎配置用 `OPENCODE_CONFIG_CONTENT` 内联注入：`permission` 全部 deny 后再放行 `hx17_*`，
  关闭自动更新、模型列表拉取、LSP 下载、默认插件、外部 skills、Claude Code 兼容、内嵌 Web UI；
- 进程以 `CREATE_NO_WINDOW` 启动，不弹窗；`OPENCODE_SERVER_PASSWORD` 随机生成，Basic 认证。

## 3. 数据模型（迁移 v2 → v3）

新增表：`user_prefs`、`turns`、`turn_events`、`actions`、`tool_jobs`、`engine_sessions`。

- `turns`：`UNIQUE(session_id, request_id)` 保证重复提交/刷新拿到同一轮；
  **部分唯一索引** `idx_turns_one_active ON turns(session_id) WHERE status IN ('queued','running','waiting_action')`
  是「每会话同时只有一个活动轮次」的数据库级保证，应用层检查只是为了给可读错误；
- `turns.status`：`queued → running → completed|failed|stopped`，`running → waiting_action → running`；
- `turn_events`：只追加，`seq` 自增；前端用 `after=seq` 拉增量，断线/刷新不丢不重；
- `actions`：`proposed → executing → done|failed`，或 `→ rejected|expired`；`claim_action`
  用条件 UPDATE 抢占，重复点击只有一个赢家；
- `tool_jobs`：`call_id` 即主键；同 `call_id` 重放返回原结果（`replayed=true`），**绝不重跑**。

## 7. 安全与可靠性决策

1. **不另写聊天循环**：模型循环、规划、工具调用全部交给引擎；本工程只负责会话/事件/工具边界。
   引擎失败不回退到其他账号或模型，直接如实报错。
2. **令牌即身份**：网关令牌由服务端在轮次启动时签发，绑定六个维度；每次调用重新查库校验
   账号启用、项目/会话未删、轮次仍在进行、连接指纹未变、目录授权未收回，任一不满足立即拒绝
   （`GatewayIdentityError` → 4xx，与业务错误区分）。
3. **错误分类**：参数/schema/越界/未知工具是业务错误（`status=error` + 结构化 `code`）；
   身份失效是 HTTP 层错误。桥侧再区分 `GATEWAY_UNREACHABLE` / `TOKEN_INVALID` /
   `TOOL_TIMEOUT`（附 `job_id`）/ `TOOL_NOT_FOUND`，不再把一切叫“工具未连接”。
4. **最终回答判定**（实测过的坑）：引擎空闲后 `/session/status` 不再返回该 key；一轮里有多条
   assistant 消息；`step-finish.reason=tool-calls` 不是最终；`summary=true` 是压缩摘要；
   `synthetic`/`ignored` 文本是内部内容；idle 可能只是短暂空档。因此：跳过以上内容，
   要求 `time.completed`，并在连续空闲 ≥1.2s 后才确认；6s 宽限仍无正文则判 `NO_FINAL_TEXT`
   并如实失败（不填占位回复）。stop 以引擎 `abort` + idle 为准，未确认空闲则标
   `STOPPED_UNCONFIRMED`。
5. **后台不被界面影响**：轮次在服务端线程跑，关侧栏/刷新不取消；重连按 `after=seq` 续拉。
   后台线程与工具调用都重新校验账号/项目/连接状态。
6. **审计**：写操作记 `agent.tool.{proposed|executed|confirmed}`，只记工具名、风险、模式与参数，
   不记 Key、不记令牌；网关不写访问日志（避免把参数写进日志）。
7. **配置与密钥不落日志**：带 Key 的引擎配置只经 `OPENCODE_CONFIG_CONTENT` 环境变量传递，
   不写磁盘、不进日志；`runtime.describe()` 不含路径、端口、令牌。

## 9. 本轮修复的真实缺陷

### 9.1 偶发 `attempt to write a readonly database`（阻断性问题）

- **现象**：`test_agent_turns` 整类串行时随机 1–3 个用例失败，单跑不复现。
- **定位**：临时探针（已删除）在失败点记录 `sqlite_errorname=SQLITE_READONLY`、
  `journal_mode=wal`、`-wal/-shm` 都存在、**同进程新建连接写入正常且同一连接永久失败**。
  即：这条连接在**打开时**就是只读的。Windows 上 `sqlite3.connect` 的可写打开若失败
  （文件刚建、被杀软/共享锁短暂独占），SQLite 的 Win32 VFS 会静默回退成只读打开，
  用户态看不到异常，`PRAGMA journal_mode` 仍返回 `wal`。
- **修复**：`db.connect()` 建连后立即用 `BEGIN IMMEDIATE` + `ROLLBACK` 验证可写，
  遇只读则关闭重连（最多 5 次，指数退避）。
- **复核**：连跑 3 轮 `test_agent_turns` 全绿；全量 198 项通过；日志中仍能看到偶发的
  「打开后不可写，重连第 1 次」——说明修复路径确实被真实触发过。

### 9.2 写探测自己造成锁排队（修复 9.1 引入，本轮又修掉）

- **现象**：真实服务 + 真实引擎时，`GET /api/turns/{id}` 会 10s 超时；界面轮询停摆。
- **定位**：探测用 `BEGIN IMMEDIATE` 且沿用 8s `busy_timeout`，每个新建连接（含每个读请求）
  都要抢写锁，并发轮询下形成锁车队。
- **修复**：探测单独设 300ms `busy_timeout`，并把「别人正在写（locked/busy）」判定为
  **连接本身可写**（直接放行），只有 `readonly` 才重连；探测结束恢复 8s。
- **复核**：轮询恢复 200 / 0.5s，stop 后 0.5s 收敛；198 项回归通过。

### 9.3 测试夹具会在任意时刻删除数据目录

`Harness` 原来用 `tempfile.TemporaryDirectory`，对象被 GC 时**随时**删除目录，而后台轮次线程可能
还在写库。改为 `tempfile.mkdtemp()` + 进程退出后由系统清理，同时消除了 ResourceWarning 噪音。

### 9.4 探针脚本自身把服务端阻塞（排查过程中的陷阱）

用 `stdout=PIPE` 起服务又从不读取，werkzeug 的访问日志填满管道缓冲区后子进程阻塞，
表现为「服务端偶发不响应」。已改为把服务端日志写文件；这不是产品缺陷，但会误导排障，记录在此。

### 13.1 能力检查不再“看起来像通过”

| 问题 | 处理 |
| --- | --- |

### 13.2 MCP 桥的启动方式与错误桥接

  用户目录里同名 `backend/` 曾会抢先导入，报 `No module named backend`；现在不依赖

- 新增 `scripts/mcp_bridge_handshake.py`：真实 Python 子进程 + 官方 MCP 客户端

### 13.3 会话级令牌（取代按轮令牌）

- 同一会话的连续多轮共用一个引擎进程，按轮签发会让第二轮拿着**已撤销**的令牌；

- 令牌里**不存** turn/mode：每次 `call` 由 `actor_for` 按会话查 `store.active_for_session`

- 用例：同会话连续两轮（`test_session_token_survives_second_turn_and_tracks_active_turn`）、
  同项目双会话并发（`test_two_sessions_keep_their_own_turns`）、无活动轮次时 409 `TURN_FINISHED`。

## 14. 生命周期补修（第三轮：三个真实反例）

### 14.1 Native 会话映射：把“存储代次”和“实际存在性”一起纳入复用条件

**真实缺陷**：`engine_sessions` 只记 `(engine_session_id, fingerprint)`。视觉能力结论
从 false 翻到 true 时引擎会换一个隔离存储目录，`_ensure_engine_session` 看到指纹没变
就把旧 ID 直接返回，而新引擎里根本没有这个会话（`GET /session/<id>` 404）。
idle 回收（原来会删存储目录）、进程崩溃、服务重启同样会踩到。

修法（三条缺一不可）：

| 条件 | 说明 |
| --- | --- |
| 连接指纹一致 | 换连接不能接着用旧会话的上下文 |
| **存储代次一致** | `engine_sessions.storage_key`（迁移 v5）= 私有存储目录的标识；目录换了，旧 ID 无意义 |
| **实际存在** | `EngineManager.session_exists()` 探测；**只有引擎明确回 404 才判不存在** |

配套改动：

- `storage_key` **不再包含 vision**：视觉结论只影响下发给引擎的模型配置，换结论需要换进程，
  但没必要换存储。原来“检查一次能力就把上下文清空”的行为不再发生。
- `_evict_stale` 在同一份存储上只换进程（`remove_dir=False`），换存储时才删旧目录。
- `sweep_idle` 只回收进程、**不删存储**：idle 之后用户的会话历史还在。
- 重建时明确恢复已公开的近期上下文（`_restore_context`）：只从 `messages` 表取
  **用户消息与最终回答**，工具中间产物/压缩摘要/内部推理不在那张表里，因此不会被带出去；
  本轮用户消息会被排除（它随后作为正式 prompt 再发一次），并明确要求“不要重复已完成的动作”。
- 探测遇到超时/连接失败/5xx **不重建、不重发**：`EngineUnavailable` 直接让本轮失败，
  避免把不确定当成 404 把用户历史和工作重做一遍。

用例（`backend/tests/test_agent_lifecycle.py`）：视觉变化保留历史、存储丢失后重建并恢复上下文、
探测网络错误不重建、idle 回收、进程崩溃、服务重启。

### 14.2 令牌有效期与缓存引擎

**真实缺陷**：`EngineManager.get` 只检查 `alive()` + 健康检查，从不看缓存实例手里的
工具令牌还有效没有。令牌过期后仍返回旧实例，`gateway.binding_for(token) == None`，
之后每个工具调用都是 401。

修法：

- `EngineManager.get` 先问 `gateway.token_state(token)`：
  `active` 才复用；`expired` → 换新凭据重建进程并**保留存储**（历史继续可用）；
  `revoked` → 抛 `SESSION_REVOKED`，**不复活**已被明确撤销的授权。
- `ToolGateway` 增加退场记录 `_retired`，把“过期”和“被撤销”分开记；
  `binding_for` 语义不变（过期即不可用），但管理器能据此选择“续期”还是“拒绝”。
- `issue_session` 仍会顶掉同会话的旧令牌，因此重建后桥拿到的一定是新凭据。

用例：过期后重建且存储不变、撤销后拒绝、以及**完整一轮**（第一轮完成后让令牌过期，
第二轮仍能正常完成并落库）。

### 14.3 停止之后不能再有副作用

**真实缺陷**：`store.request_stop` 只是打标记；`actor_for` 找的是 `active_for_session`，
被请求停止的那一轮仍是 active，于是停止之后的工具调用照样执行、照样写文件。

修法：

- `actor_for`：活动轮次 `stop_requested_at` 非空 → `STOP_REQUESTED`（409），不再执行新动作。
- `call`：待确认动作在创建前再查一次停止标记，避免“停止瞬间又冒出一张确认卡”。
- `execute_action`：确认时检查**原操作状态**——所属轮次被停止或已 failed/stopped 一律拒绝，
  并保留目录授权复查。
- 已经跑起来的任务如实报告：执行期间收到停止 → 结果里带
  `stop_requested_during_execution` 与说明（动作已发生、不回滚）；`_finish_stopped`
  会列出停止时仍标记为执行中的任务名，并明确“结果未知，不能假设已完成或已回滚”。
- abort 未确认空闲 → `EngineManager.quarantine()`：结束进程 + 撤销令牌（旧调用不可能再产生
  副作用），存储保留；轮次记 `STOPPED_UNCONFIRMED`，界面不会把“标了 stopped”当成“业务都停了”。
  已确认空闲则保留引擎，不打断后续使用。
- `_fail` / `_finish_stopped` 会把该轮遗留的 `running` 任务收成失败，避免同一 `call_id`
  永远停在“请稍后再查”。

用例：停止后写文件被拒且文件不存在、停止后确认动作被拒、撤销令牌后调用 401、
未确认空闲时隔离引擎并如实报告（含“旧令牌失效、下一轮换新引擎新令牌”）、确认空闲时不隔离。

### 14.4 模型与视觉证据统一到一个解析器

**真实缺陷**：`prefs.model`（对话里另选）与 `connections.model`（连接里保存）是两套选择；
`verified_vision` 只读 `capabilities.vision`，不看证据属于哪个模型——A 验证过的视觉能力
会被声明给 B。

修法：

- `identity.resolve()` 成为唯一出口：模型 = 偏好（仍在可用列表）否则连接模型；
  视觉 = 证据覆盖 `(base_url, provider, model, key_fingerprint)` **且 `checked_model` 等于
  当前模型**，否则按无视觉处理（`vision_reason` 给出 `stale/unchecked/unsupported`）。
- `connections.check` 探测的也是**当前实际模型**，`checked_model` 记的就是它；
  `view()` 的 `capabilities_stale` 同样按当前模型判断，并新增 `effective_model`。
- 新增 `store.clear_model_pref()`：`PUT /agent/me/preferences` 传空字符串可以清掉另选的模型，
  回到连接默认（原来 `COALESCE` 会让它永远清不掉）。

用例：切到另一个模型后视觉结论失效且 `capabilities_stale` 为真、切回来恢复。

## 15. 基线读取瞬时失败（第四轮：最后一处真实反例）

协作者用新脚本 `verify_baseline_transient.py`（同目录，本轮**只读、未修改**）复现：
旧终答已存在，发起前读取“已有消息 ID 集合”失败一次，后续读取恢复正常，新请求先短暂空闲
（`idle_blip=3s`）。独立运行结果：

```json
{"reads":5,"turn_status":"completed","answers":["OLD-ANSWER","OLD-ANSWER"],"old_answer_not_reused":false}
```

修复后原样重跑同一脚本：

```json
{"reads":9,"turn_status":"completed","answers":["OLD-ANSWER","NEW-ANSWER"],"old_answer_not_reused":true}
```

### 15.1 根因：把“读不到”当成“空历史”

`runner._message_ids` 原来是：

```python
try:
    messages = self._manager.messages(instance, engine_session, limit=500)
except engine_module.EngineUnavailable:
    return set()          # ← 这里是错的
```

边界的语义是“**已经存在**的消息 ID”。返回空集合等于宣称“这个会话此前一条消息都没有”，
于是轮询阶段 `_new_messages` 把整段历史都判成本轮新增；新请求短暂 idle 时，上一轮的终答
（`time.completed` 已置位、`finish=stop`）满足 `_pick_final` 的全部条件，本轮被标成
`completed` 并把旧回答又写进 `messages` —— 假成功 + 旧答重复 + 真正的新答被丢弃。
这一条比“报错”更糟：界面上看不出任何异常。

### 15.2 修法：有界只读重试，拿不到确定基线就不发请求

| 要点 | 实现 |
| --- | --- |
| 失败即重试 | `BASELINE_READ_ATTEMPTS = 3`，间隔 0.25s / 0.5s，**只读 GET**，不计费、不发 prompt |
| 形状校验 | 读到了消息但一个 `info.id` 都取不到 → 同样判不可靠（`BASELINE_UNAVAILABLE`） |
| 仍不确定 | 抛 `EngineUnavailable("BASELINE_UNAVAILABLE")`，本轮在 `prompt_async` **之前**失败 |
| 失败文案 | `_engine_message` 明确写“本轮没有向模型发送任何请求，因此不会重复执行；稍等重新发送即可” |
| 不再兜底 | `_poll` 的 `baseline` 改为必填，删掉 `baseline = baseline or set()` |

关键顺序保证：`_message_ids` 在 `_run` 里位于 `prompt_async` **之前**，异常被同一处
`except EngineUnavailable` 捕获并 `_fail`，所以“失败”与“已发出请求”互斥，不存在
“失败了但请求已经发出去”的中间态。也**没有**做任何内容字符串去重——判定只认消息 ID。

### 15.3 同类出口一并核对（不只改测试命中的那一条）

| 位置 | 原行为 | 现在 |
| --- | --- | --- |
| `_message_ids`（唯一调用点 `_run`） | 失败 → 空集合 | 有界重试 → 失败即 `BASELINE_UNAVAILABLE` |
| `_poll` 停止分支的收尾读取 | `except EngineUnavailable: messages = []` | 保留空同步（这里不参与完成判定），但把“无法读取、未保存的中间输出可能已丢失”写进收尾说明 |
| `_poll` 主循环读取 | 连续失败计数后 `ENGINE_LOST` | 不变（异常分支不 sync、不判定完成，本来就安全） |
| `_poll(baseline=None)` | `None → set()` | 参数必填，取消兜底 |
| `session_exists`（上一轮） | 只有 404 才判不存在 | 不变 |
