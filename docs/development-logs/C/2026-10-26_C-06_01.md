# C-06 开发（训练、版本与发布隔离）

- 时间：2026-10-26（北京时间）
- 负责人：第三人业务工具任务，本轮由 WorkBuddy 在当前工作区执行
- 开发执行平台：WorkBuddy
- 分支 / 起点提交 / 接口版本：无 `.git` 元数据；业务工具接口 v1，新增 `training.start`、`training.get_state`，并把页面训练路由与工具层统一到 `services/training_runner.py`
- 本次目标和原问题：
  - 训练只有页面入口；页面允许同时启动多个训练进程（`training_processes` 字典只做记账，不做互斥），与"一台机器同时只跑一个训练、忙时明确拒绝、不排队"直接冲突。
  - 训练实现写在路由函数里，工具层若复用就会分叉出第二套实现（下载数据、解压、选基础权重、上传结果），两边行为必然不一致。
  - 重启后没有任何"训练到底跑没跑完"的可恢复依据，容易被自动重投。
  - 发布/下架的影响面只在底层服务内部计算，Agent 调用前看不到"会归档哪些模型"。
- 给 AI 的材料与关键词：任务书 C-06（确认数据集版本、父模型、模态、参数、输出与资源归属；单机单训练；训练建新版本不覆盖父模型；保留任务引用与真实状态/指标；指标来源不同不得声称提升；发布/下架预览影响面且只限本项目；重启后不自动重投；如实声明取消能力）；`model_registry_service.start_incremental_training`、`compare_models`、`publish_model`、`ModelPublishConflict`；`training_service.run_training`
- 修改文件、具体业务及修改前后差异：
  - 新增 `services/training_runner.py`：单次训练的唯一实现 + 机器级占用表 `training_lock(lock_id=1, owner, holder_pid, acquired_at)`。
    - `acquire_training_lock` 在 `BEGIN IMMEDIATE` 事务内检查当前占用：持有进程存活则抛 `TrainingBusy`（`code="TRAINING_BUSY"`），已死则回收；**没有排队**。
    - `set_lock_holder` 把占用指向真正的 worker pid；`transfer_training_lock` 把"预留"转给模型行；`release_training_lock` 只释放自己持有的那把。
    - `run_training_job(model_id, dataset_id, base_model, epochs, batch_size, parent_model_id, database_path)`：写 `TRAINING` → 下载数据集 zip → `validate_dataset_archive` → `safe_extract_dataset` → `build_runtime_yaml` → 选父权重 / 多模态基线 / `weights/<base_model>` → `run_training` → 上传 `models` 桶 → 写 `COMPLETED` + `train_result` + `metrics_json`；任何异常写 `FAILED` + 错误文本；`finally` 一定释放占用并删除临时目录。
  - `routes/model.py`：`run_training_process` 变成 `run_training_job` 的薄包装；`/create` 与 `/<parent>/incremental` 在起进程前 `acquire_training_lock`，`TrainingBusy` 时返回 **409** 并删除刚插入的模型行（不留半条 `TRAINING` 垃圾），起进程失败时释放占用再抛；新增 `_lock_db_path()` 取 `db.db_path`，保证页面写入的库和持锁的库是同一个（否则换库部署或测试时两侧各持一把锁，"单机单训练"形同虚设）；新增 `_mark_training_taken_slot()`，拿不到 worker pid 时释放占用而不是留下回收不了的死锁。
  - `utils/schema_migrations.py`：`training_lock` 进入正式 schema（`CREATE TABLE IF NOT EXISTS`），不再靠首次调用时临时建表。
  - `services/tool_handlers.py::TrainingStart`
    - `prepare` 逐项检查：父模型必须 `status in {1,3}` 且有 `model_object_key`（`PARENT_MODEL_NOT_READY`）；数据集与父模型单/多模态一致（`MODE_MISMATCH`）；主模态一致（`MODALITY_MISMATCH`）；`read_lock` 有占用则 `TRAINING_BUSY`（附当前 `holder`）。预览给出父模型、数据集（含 `status`）、真实参数、`new_model.version = 父 version + 1`、`output` 写明"不覆盖父模型权重"。
    - `execute` 先抢锁（owner 用 `pending:<uuid>` 预留），抢不到抛 `ToolRefused("TRAINING_BUSY")`；`start_incremental_training` 建子模型行后把占用转给子模型 ID；启动进程失败时释放占用并把子模型置 `FAILED(2)`，抛 `TRAINING_LAUNCH_FAILED`。
    - `_launch_training` 默认起 daemon `multiprocessing.Process(run_training_job)` 并 `set_lock_holder`，可被 `training_launcher` 注入替换（测试用）。
  - `services/tool_handlers.py::TrainingState`：`models.status` 映射为 `training/succeeded/failed/published/cancelled`，只读，**不重投训练**；返回指标时带指标来源。
  - `services/tool_handlers.py::ModelCompare`：除父子指标外给出 `comparable` 与 `_compare_conditions`，评测条件不同（数据集、模态、epochs 等不一致）时明确"不能直接归因于模型改进"。
  - `services/tool_handlers.py::ModelPublish` / `ModelUnpublish`：预览列出同模态域将被归档的**完整模型 ID 清单**（发布）或受影响模型清单（下架）；执行时在底层事务内核对清单，变化则 `PREVIEW_STALE`；两者都要求 `model:publish-global`，且解析出的模型必须属于用户自己的项目范围，不能归档其他项目或系统默认模型。
- 优化原因：训练只有一份实现，页面与 Agent 不可能跑出两种行为；占用是机器级单行记录，任何入口都要先过这一关；重启后靠 `models` 行读结果，绝不自动重投；发布影响面在写库前可见。
- 对第一人/第二人的接口、迁移和旧页面影响：
  - 第二人：需裁决 `model:train`、`model:read`、`model:publish`、`model:publish-global`、`dataset:read`；`resolve_resource` 的 `model.version` 必须是真实版本号（预览的 `version+1` 依赖它）；`training.start` 的 `supports_cancel=False`，不要给前端挂取消；重启协调方应在确认无存活训练进程后调用 `reconcile_unfinished()`，训练本身靠读 `models` 行恢复，不重投。
  - 第一人：`/api/model/create` 与 `/incremental` 新增 **409 忙时拒绝**（新行为，之前会并行启动）；训练落库字段、状态值、失败文案不变；`training_lock` 表由启动迁移自动创建。
  - 迁移：新增 `training_lock` 单行表，随 `utils/schema_migrations` 自动建，无需手工改库。
- 数据/文件保护方式和输出位置：训练临时目录 `TEMP_DIR/model_training_<model_id>_<rand>`，结束即删；权重上传到 `models` 桶；测试用 `training_launcher` 注入，不真正训练、不占 GPU。

- 未完成、风险和下一步：
  - 训练的真实取消能力：`supports_cancel=False`，如实声明不支持；如需取消，需要单独的"终止训练"业务动作（当前页面也没有）。
  - `training_lock` 只能防本机（同一个 SQLite 文件）；多机部署需要换成外部锁。
  - 拿不到 worker pid 时会释放占用（避免死锁），代价是极端情况下可能并行；真实 `multiprocessing.Process` 一定有 pid，只有测试替身会走到这条分支。
