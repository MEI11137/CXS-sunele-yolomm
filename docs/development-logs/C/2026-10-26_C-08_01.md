- 时间：2026-10-26（北京时间）
- 负责人：第三人业务工具任务，本轮由 WorkBuddy 在当前工作区执行
- 开发执行平台：WorkBuddy
- 分支 / 起点提交 / 接口版本：无 `.git` 元数据；业务工具接口 v1，新增 `dataset.transform`、`dataset.register_candidate`
- 本次目标和原问题：
  - 改造数据集（改类名、筛类别、重划 split、批量复制/改名图片、连带 X 模态与标签）原本要靠人手跑脚本，没有任何"先看清单再动手"的环节。
  - 同名不同内容、同图不同标签、重复图、train/val 泄漏这几类问题一旦混进训练集，只会在训练结果变差时才被发现。
  - 类别映射靠猜：调用方给一个 `class_map`，代码不知道该源数据到底有哪些类。
- 给 AI 的材料与关键词：任务书 C-08（先检查后给出来源/输出/改动清单/类别映射/冲突方案/diff 预览；确认后生成候选新目录或版本，默认保留源，不静默覆盖；批量改名/复制/筛选图像、X 模态与标签；显式处理类别 ID、同名不同内容、同图不同标签、重复；不猜映射；检查 train/val/test 泄漏并在冲突时暂停输出确认；标签改动基于人工确认结果，视觉建议保持待复核；输出含来源、规则、清单、校验报告；业务校验后才登记为正式训练数据；仅在用户明确要求时合并原数据集与反馈）
- 修改文件、具体业务及修改前后差异：
  - 新增 `services/dataset_transform_service.py`
    - `_plan(scan, arguments, source, provided_classes)`：**先算不改**。
      - 源类别只认扫描出来的真实类别（或调用方显式给的 `class_names`）；一个都没有 → `CLASS_NAMES_REQUIRED` 直接返回。
      - `class_map` 里有源数据不存在的类别 → `CLASS_MAP_UNKNOWN`；`keep_classes` 里有不存在的 → `CLASS_FILTER_UNKNOWN`；多个源类映射到同一名字 → `CLASS_MAP_DUPLICATE`；筛选后为空 → `CLASS_FILTER_EMPTY`。
      - `split_policy` 校验：未知划分名 `SPLIT_POLICY_INVALID`、比例之和不为 1 `SPLIT_POLICY_SUM`、train/val 为 0 `SPLIT_POLICY_EMPTY`、样本不在 train/val/test 下且没给比例 `SPLIT_UNKNOWN`。
      - 逐样本算 `kept_ids`（新类别索引）与 `dropped`（被筛掉的标注条数，记 `ANNOTATIONS_DROPPED` 警告）；按 RGB sha256 去重，重复样本记 `DUPLICATES_SKIPPED` 不再进入输出。
      - **泄漏检查对全部重复组求值**（不是只看进入输出的样本）：同一 sha256 落在不同 split 即 `SPLIT_LEAKAGE`，并作为冲突阻断。
      - 输出 `target`（名称、描述、单/多模态、主/次模态）、`class_names`、`class_map`、`counts`、`sample_count`、`warnings`、`conflicts`、`leakage`、`blocked`、`ignored_arguments`。
    - `plan_from_dataset(...)`：下载数据集归档 → `safe_extract_dataset` → 扫描，`source` 里带 `archive_sha256`；名称已被数据集或候选占用 → `NAME_CONFLICT`；有 `include_feedback` 时给 `FEEDBACK_MERGE` 警告并在 `source.merge_feedback` 标出。
    - `plan_from_directory(...)`：源为授权目录，扫描的 `blocking` 问题直接并入 `conflicts`（最多列 20 条）。
    - `build_candidate_from_dataset` / `build_candidate_from_directory`：`blocked` 时抛 `TransformBlocked`；否则 `_materialize` 落盘。
    - `_materialize`：写 `images/<split>/<key>`、可选 `images_<secondary>/<split>/<key>`、`labels/<split>/<key>.txt`（`_rewrite_label` 按新类别索引重写类别 ID）、`data.yaml`（多模态带 `modalities`/`modality_used`）、`manifest.json`（`name/description/dataset_mode/primary_modality/secondary_modality/class_names/class_map/rules/source/split_counts/sample_count/warnings/blocking_reasons/entries/created_at/generator`）。**只处理计划里被纳入的样本**，重复与越界样本不会混进输出。
    - `_relative_key`：去掉前导 split 目录，避免 `images/train/train/a.txt` 这类路径重复。
    - `register_candidate(adapter, principal, candidate_id)`：把候选目录压成 zip（排除 manifest）→ `import_dataset_archive` → 候选记录置 `status='registered'` 并回填 `dataset_id`。**只有到这一步才成为正式训练数据**。
    - 候选表 `dataset_candidates`：保存候选目录、计划、状态（`prepared`/`built`/`registered`）。
  - `services/tool_handlers.py::DatasetTransform` / `DirectoryTransform` / `DatasetRegisterCandidate`：预览即 `_plan` 结果（`blocked`/`conflicts`/`ignored_arguments` 全透出），执行时重新算计划并比对，不一致抛 `ToolConflict`；`register_candidate` 前校验候选状态与项目归属。
  - `services/business_tool_specs.py`：`dataset.transform`（`kind="dataset"`）、`directory.transform`（`kind="directory"`）、`dataset.register_candidate`（`kind="project"`）；`class_map` 用 `{"type": "object", "values": {"type": "string"}}` 校验。
- 优化原因：把"能不能改"和"改完之后长什么样"提前到写盘前；类别映射必须来自真实源类别而非猜测；泄漏、重复、同名冲突在预览阶段就拦住；源数据默认不动，产物是新目录/新版本。
- 对第一人/第二人的接口、迁移和旧页面影响：
  - 第二人：需裁决 `dataset:read`/`dataset:write`/`directory:read`/`directory:write`；注入 `candidate_root`（候选目录根，未注入时用 `work_dir`）与 `storage_client`；`resolve_resource` 的 `dataset.version` 要能反映内容变化。
  - 第一人：无旧接口改动；页面上没有改造入口，新增能力只在 Agent 侧。
  - 迁移：新增 `dataset_candidates` 表，随服务首次使用建表。
- 数据/文件保护方式和输出位置：候选写到 `candidate_root/<candidate_id>/`，**源数据集压缩包与源目录都不修改、不删除**；测试断言源文件字节不变；manifest 只记相对路径与 sha256，不含路径以外的私有内容。
- 验证内容及结果：
  - `test_transform_rewrites_classes_and_registers_a_new_dataset`：改类名后 `labels/` 里类别 ID 被重写、`manifest.json` 存在且规则可读；`register_candidate` 后新数据集出现；源数据未变。
  - `test_transform_refuses_to_split_leaking_duplicates`：相同图片跨 split 时 `blocked` 且冲突含 `SPLIT_LEAKAGE`，不产出候选。
  - 定向回归：C-01~C-07 全部用例保持通过。
