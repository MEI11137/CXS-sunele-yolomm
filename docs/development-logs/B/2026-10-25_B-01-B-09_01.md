- 选择本次优化方式的原因：
  1. **独立包 `agent/` 而不是散落到 `routes/`、`services/`**：三人并行开发，第二人边界最容易被他人改动冲掉；独立包 + 单一注册入口，合并时冲突面只有 `app.py` 两行。
  2. **动作确认、权限校验放程序层而不是提示词**：任务书要求这些"不能仅靠提示词约束"。因此 `permissions.require_access`、`actions.confirm`（原子领取 + `request_key` 幂等）、`_plan_gate`（多步写入先要计划）都是代码强制。
  3. **凭据加密只用标准库**：当前环境连 pip 都装不上（代理 502），引入 `cryptography` 会让队友无法启动；改用 HMAC-SHA256 流加密 + Encrypt-then-MAC，带 `AG1` 版本前缀，将来换 AES-GCM/KMS 可按前缀兼容旧数据。主密钥独立成文件，数据库被单独拷走解不出 Key。
  4. **测试用 `unittest` 而不是 pytest**：本机 `pvdetect` 环境没有 pytest 且无法联网安装；`unittest` 零依赖即可跑，pytest 也能直接收集，不牺牲队友的可运行性。
  5. **替身工具显式标注**：第三人工具未就绪时也能演示全链路，但结果一律带 `is_stub=True`、`AGENT_ALLOW_STUB=0` 时从工具清单消失，避免"假成功"混进真实业务。

- 对第一人/第三人的接口和迁移影响：
  - **数据库**：只新增 `agent_*` 表（`agent_project/resource/model_connection/session/task/event/action/manual/handoff_note/tool_grant` 等），不改动既有 `user`/`detections` 等表；`store.ensure_schema` 幂等，重复调用不报错。旧资源通过 `legacy.migrate_legacy_resources()` 补归属，默认策略 `shared_readonly`。
  - **第一人（前端）**：接口前缀 `/api/agent`，共 43 条路由；成功沿用既有 `{code, msg, data}`，失败时 HTTP 状态码与语义一致，`data.code` 是稳定字符串（如 `AGENT_ACTION_STALE`），`data.execution_state` 区分"未执行/已执行/未知"。事件流 `GET /sessions/<id>/events?after=<seq>` 与 SSE `/events/stream` 都用递增 `sequence`，断线重连按序号去重即可。确认卡流程：`POST /messages` 返回 `status=awaiting_action` + `action`，用户点击后 `POST /actions/<id>/confirm`（带 `expected_revision`，不一致返回 `AGENT_ACTION_STALE`）。
  - **第三人（业务工具/MCP）**：实现 `list_tools()` 返回 `ToolSpec`，并实现 `prepare_tool/execute_tool/get_operation/get_resource_state/cancel_operation`，调用 `runtime.set_business_backend(obj)` 即接入；`execute_tool` 会收到 `request_key`，相同 `request_key` 必须返回同一结果（防重复执行）。外部 MCP 工具需带 `server_id`，否则只读放行无法匹配。真实业务工具同名时优先于替身。
  - **配置**：全部走环境变量（`AGENT_SECRET_PATH`、`AGENT_MAX_STEPS`、`AGENT_TIME_BUDGET_SECONDS`、`AGENT_ALLOW_STUB` 等），默认值可直接启动。
