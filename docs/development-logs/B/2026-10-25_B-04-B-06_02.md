- 本次目标和原问题：
  第一轮 19 个用例只能证明"设计的主干路径成立"，不能证明"其它路径也不出问题"。本轮做第二轮自测：静态扫描 + 逐条打全部接口 + 边界/意图/并发/重启场景，把发现的问题修掉并补成回归用例。结果发现 3 个真实缺陷（都是"用户会直接看到错误信息"的那一类），另有若干脚本自身的假设错误不计入缺陷。
- 给 AI 的材料及关键词：本轮不需要外部材料，全部基于上一轮代码与本机实测；关键词：进度分支、意图分类、改目标、状态语义、确认卡标题、并发确认。仍使用假网关与替身工具，未使用任何真实 Key。
- 修改文件、功能和修改前后差异：

  1. **`agent/runtime.py` `_progress_reply`（进度询问分支）**
     - 修改前：回复里直接拼内部状态码，用户会看到 `当前任务状态：awaiting_action`；并且 `"action": None` 写死，任务明明卡在一张待确认卡片上，问"做到哪一步"却拿不到这张卡。
     - 修改后：状态走 `tasks.STATUS_LABELS` 转中文（"等待你确认操作"）；存在待确认动作时，回复里明确写"有一项操作等待你确认：<标题>"，并在返回值里带出该 `action`，前端据此可以继续渲染卡片。

  2. **`agent/runtime.py` `_decide_final_status` + `_apply_change`（改目标后的状态语义）**
     - 修改前：用户说"改成只检测第一张"后，旧确认被作废、任务被重置为 `planning`；如果模型这一轮只回了一句文本，`_decide_final_status` 因为"没有步骤"直接判 `completed` —— 什么都没执行却显示"已完成"，这是会误导用户的假成功。
     - 修改后：新增 `tasks.SUMMARY_REPLAN` 常量标记"目标变更、等待重新规划"；该状态下且无任何步骤时，保持 `planning`（不判完成）。任务仍是活动任务，用户下一句会接着同一个任务重新规划。改动只在"改目标且模型只回文本"这一条窄路径上生效，普通问答与只读任务不受影响。

  3. **`agent/actions.py` 确认卡标题缺失**
     - 修改前：`create_action(tool_title=...)` 只把标题拼进了 `parameters_summary`，标题本身没有落库，`_action_view` 里也没有该字段 —— 前端只能看到 `run_detection` 这种内部工具名，做不出可读的确认卡。
     - 修改后：标题随 `preview_json` 一起持久化（`preview["tool_title"]`），`_action_view` 暴露 `tool_title`，取不到时回退到 `tool_name`。没有加数据库列，已有库不需要迁移，历史动作也能正常读出（只是回退为工具名）。

  **新增/调整测试**：`tests/test_agent_backend.py` 增加 3 个回归用例（进度分支中文化并带出动作、改目标不伪装完成、停止意图在有待确认动作时也生效），用例数 19 → 22。

- 选择本次优化方式的原因：
  1. **不新增数据库列**：`tool_title` 若加成正式列，需要 ALTER TABLE 迁移，队友拉下代码后旧库要跑迁移；改成写进已有的 `preview_json`，零迁移、零兼容风险。
  2. **状态语义只在窄路径收紧**：直接"planning 一律不判完成"会破坏正常问答（普通一句话回复会让任务永远挂着），因此用 `SUMMARY_REPLAN` 精确标记，只在目标刚变更时生效。
  3. **中文化放在服务端**：状态文案如果交给前端映射，三端（Web、文档、后续小程序）各写一份必然漂移，放在 `tasks.STATUS_LABELS` 一处更稳。
  4. **补测试而不是只改代码**：这三处都是"看起来能用、实际说错话"的缺陷，只有用例能防止回退。

- 对第一人/第三人的接口和迁移影响：
  - **无破坏性变更**，接口版本仍为 `1.0.0`。新增字段：`action.tool_title`（确认卡标题）、`action.preview.tool_title`；进度分支返回值 `action` 由 `null` 变为可能返回对象。前端按"可能为 null"处理即可，无需改动。
  - **无数据库迁移**。`agent_action.preview_json` 里多一个 `tool_title` 键，旧数据无此键时回退为工具名。
  - **第三人**：`ToolSpec.title` 现在会真正出现在前端确认卡上，请填写面向用户的短标题（如"图片检测"），不要写内部编码。

- 未完成、风险及下一步：
  1. **SSE 与生产 worker 模型**：`/events/stream` 会占用一个请求线程（最长 60 秒）。Flask 开发服务器是 threaded 的没问题，但 gunicorn 同步 worker 数量有限时会占满。下一步：生产改用 `--threads` 或提供"只走轮询 `GET /events?after=`"的降级开关（轮询接口已经可用）。
  2. **`grants` 撤销是幂等的**：重复撤销同一授权返回 200 而不是 404（`revoke_grant` 未加 `revoked_at IS NULL` 条件）。判定为可接受（DELETE 幂等），但若前端靠 404 判断"已撤销"需要改为读 `list_grants`。
  3. **真实模型下的意图分类**：`_STOP_TOKENS`/`_CHANGE_TOKENS` 是规则匹配，"不用了""算了"这类表达可能漏判。接入真实模型后需要收集实际话术补齐词表，或改为"模型给意图 + 规则兜底"。
  4. **`_progress_reply` 仍假设任务未被中断**，若状态是 `interrupted`/`unknown`，结尾那句"可以继续推进"需要按状态改写。
  5. 交接笔记的 `needs_recheck` 目前只在纠错时清零，尚无"定期核对"机制（B-08 后续项）。
