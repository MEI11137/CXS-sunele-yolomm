- 本次目标、原问题及源码依据：
  - 目标：B 侧的 Agent 运行时能**真实列出并调用 C 的业务工具**，且"预备 → 确认 → 执行"全程绑定同一条业务预备记录。
  - 原问题（逐条用源码确认，不是推测）：
    1. `agent/tools/business.py:92` 调 `self._backend.list_tools()`（无参），C 的 `services/business_tools.py:299` 是 `list_tools(principal:int)` → `TypeError`。
    2. 同一行用 `isinstance(spec, ToolSpec)` 过滤，而 C 的 `list_tools` 返回 `list[dict]`（`business_tools.py:308-311`）→ 即使不报错也会被**整体丢弃**，模型看不到任何业务工具。
    3. `agent/runtime.py:563` 调 `provider.prepare(...)` 后只取 `preview`，把 C 返回的 `operation_id`（预备记录）直接丢掉；而 C 的 `execute_tool(principal, prepared_id, request_key)`（`business_tools.py:532`）**必须**拿到这条记录才执行 → 确认后根本没法执行。
    4. `agent/runtime.py:651-657` 重试时把 `request_key` 改成 `f"{key}_{attempt}"`，等于绕过 C 的 `request_key` 幂等（`business_tools.py:546-551`），一次动作可能被执行两次。
    5. `agent/runtime.py` 原逻辑在 `prepare` 抛 `AgentError` 时只写 `preview_error` 然后**照样建确认卡**，违反整合文档 7.3.6"prepare 报错或 preview.blocked 时不能生成可确认后继续执行的有效动作"。
    6. C 的所有工具（含只读）都要求先 `prepare_tool` 再 `execute_tool`，B 的"只读直连"路径没有预备记录可用。

- 为何这样改、复用了哪些现有实现：
  - 只做"翻译"，没有重写 C 的 handlers，也没有在 B 里再实现一遍业务逻辑。
  - 契约识别用**签名检查**而不是异常兜底：`TypeError` 兜底会把业务内部真实的 `TypeError` 一起吞掉，正是整合文档 7.1 明确禁止的做法。
  - `prepared_id` 走 `agent_action` 的独立列而不是塞进 `preview` 里凑合：预览是给人看的，绑定是执行依据，两者生命周期不同（预览可能被前端裁剪）。同时保留 `preview.prepared_id` 供前端排障。
  - 只读工具"服务端补预备"是 C 的硬约束（`execute_tool` 必须带 `prepared_id`），不是 B 偷懒；该预备不产生确认卡，因为只读无副作用。
  - `release_prepared` 用 `getattr` 能力探测而非签名嗅探，只有业务 provider 实现了才会调用。
- 数据迁移/权限/接口/旧页面影响：
  - 迁移：仅 `agent_action.prepared_id TEXT` 一列，`ALTER TABLE ADD COLUMN`，旧库自动补齐，无需人工干预；`SCHEMA_VERSION` 升到 2。
  - 权限：无放行改动。C 的 `PermissionError` 映射为 `AGENT_TOOL_NOT_GRANTED`(403)，`FileNotFoundError`→`AGENT_RESOURCE_NOT_FOUND`(404)，`ToolConflict`→`AGENT_ACTION_STALE`(409)；未声明的异常**原样抛出**，不伪装成业务失败。
  - 接口：无新增/删除路由。`/api/agent/tools` 的返回结构不变，只是内容由替身变成真实业务工具（`cancel_scope` 为新字段）。
  - 旧页面：`web-vue` 与 `web-haixun` 均未改；C 的业务路由未动。
