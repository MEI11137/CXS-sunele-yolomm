# INT-05 开发日志：人工提交、个人发布与跨项目业务边界

- 日期：2026-10-26
- 分支：`integration/haixun-v1`
- 关键词：INT-05；LLM 工具清单排除人工提交和扩权配置；人工页面才写最终标签；复核提交变更通知；发布 SQL 按 owner/project 隔离；移除普通用户 publish-global 依赖；精确归档清单；默认模型只读；显式跨项目引用与输出归属。

## 1. 人工复核不能成为模型自行执行的工具（10.1）

**问题**：`review.submit_human`、`draft.assign_splits`、`mcp.save_connection` 和其它工具一样进 LLM 清单，模型可以直接写最终人工标签、替人做样本划分、改连接配置（含启动命令与凭据引用）。

**做法**：

- `services/business_tool_specs.ToolSpec` 新增 `agent_executable`，`_tool()` 把它写进描述符的 `audience`（`agent` / `human_page`）。标记为 `human_page` 的三个动作：
  - `review.submit_human`：最终人工标签；
  - `draft.assign_splits`：样本划分；
  - `mcp.save_connection`：连接配置与扩权设置。
- `BusinessToolAdapter.list_tools` 直接跳过 `agent_executable=False`，模型看不到这些动作。
- `prepare_tool` / `execute_tool` 新增**服务端入口参数** `entry`（默认 `ENTRY_AGENT`，人工页面传 `ENTRY_HUMAN_PAGE`）。`_require_entry()` 在参数校验与依赖检查之前执行：Agent 入口一律 `PermissionError`。
  - 不认请求体里的 `human=true`，也不认一张普通确认卡：入口是服务端调用方式，不是模型参数。
  - `execute_tool` 也检查：即使有人手工插了一条 `prepared` 记录，Agent 入口同样执行不了（有用例覆盖）。

**人工页面才是唯一写入口**：`routes/detection.py` 的 `/records/<id>/human-review` 继续走 `services.review_service.submit_human_review`（受保护的人工路由 + 归属校验），不经过 Agent 的工具链。

**复核提交后的变更通知**：

- 人工提交成功 → `resources.ensure()` + `resources.bump()` 递增索引版本 → 把 `business.changed` 事件交给 `BusinessNotifier`。
- `BusinessNotifier` 现在**先核实再接力**：读取 `agent_resource.revision`，只有「当前版本 > 任务里记录的版本」才追加事件；版本没动或索引里查不到该对象 → 计数 `unchanged`，**什么都不发**，任务继续等待。事件里带的是核实后的真实版本。
- 通知/索引失败不影响已经落库的人工决定（try/except 包住，只丢附加链路）。

## 2. 发布必须限定本人和实际项目（10.2）

**问题**：`_preview_model_publish` 与 `model_registry_service.publish_model` 的归档 SQL 都按「整张 models 表 + 同模态」筛选，一个用户发布会归档掉别人项目里的已发布模型；`model.publish` / `model.unpublish` 还挂着 `model:publish-global` 全局权，普通用户在工具清单里根本看不到，等于「发布能力只对管理员开放」。

**做法**：

- `agent/resources.scope_ids()` / `model_scope_ids()`：从 `agent_resource` 取**同一 owner 且同一 project** 的业务 ID；未登记时先按真实归属幂等补登记，仍查不出来就只返回自己（绝不退化成整表）。
- `services/model_registry_service.publish_model(..., scope_model_ids=...)`：
  - 待归档集合 = 同模态 **且 id ∈ 授权范围**；
  - `expected_archived_model_ids` 仍在同一事务内比对，不一致抛 `ModelPublishConflict`（预览清单变化必须重新确认）；
  - `UPDATE` 改成**精确 ID 清单**（`WHERE id IN (...)`），不再按模态整表更新；
  - `PublishResult.archived_model_ids` 返回真正被归档的清单。
- `BusinessToolAdapter._model_scope()`：范围内每个模型都重新 `resolve` + `model:publish` 授权，任一不通过就整体拒绝；`_publish_model` 每次执行重新授权，确认时带的范围只能缩小。
- 预览里带 `scope_model_ids`，确认后按它复核——范围本身不可由参数扩大。
- `model.publish` / `model.unpublish` 规格移除 `global_actions` 与 `requires` 里的 `model:publish-global`，改为只看模型自身的 `model:publish`。`policy_bridge.ADMIN_ONLY_ACTIONS` 仍保留该动作（管理员专用的全局动作仍 fail-closed），只是普通用户发布不再依赖它。
- 页面路由 `POST /api/model/<id>/publish` 也传 `model_scope_ids`，并在发布/撤销发布后 `resources.bump()`，使旧预览与旧确认失效。
- 默认共享模型属于系统账号，普通用户的范围里天然不含它们；`model:publish` 对共享只读资源也不通过 → 默认模型不可被普通用户归档、撤销或覆盖。

## 3. 检测与引用（10.3）

- `detection.run` 新增可选 `output_project_id`：
  - 不传 → 输出项目 = 原图所在项目（`output_project_source: asset_project`）；
  - 传了 → 对该项目做 `detection:create` 授权，不可写直接 `PermissionError`（`explicit`）。
- 预览新增 `model_project_id` / `output_project_id` / `output_project_source`，并保留 `model_source: cross_project_readonly`：跨项目**只读引用**模型不再阻断，`MODEL_NOT_PUBLISHED` 与模态配对规则不变。
- `execute` 改为核对「原图仍在预览时的项目」＋「输出项目仍是预览时的项目」，任一变化抛 `ToolConflict`；`business_refs` 的 `project_id` 改成输出项目，检测记录随之归输出项目，**模型归属与状态一行不动**。
- 图片与 X 配套、模态、类别契约保持原严格检查（有用例）。

## 5. 未做与风险

- 人工页面的 `review.submit_human` / `draft.assign_splits` / `mcp.save_connection` 目前仍由既有服务/REST 路由承担，并没有真的改造成「调用适配器 + `ENTRY_HUMAN_PAGE`」；适配器侧入口已就位，接线属于前端联调（INT-07）范围。
- 归档范围依赖 `agent_resource` 的登记质量：从未登记且推导不出归属的模型只会「不归档任何旧模型」，不会误归档，但会让同一项目出现多个已发布模型——这种情况在装配报告里看不出来，后续可加一条可观测计数。
- `detection.run` 的 `output_project_id` 尚未在前端暴露，只在 Agent 工具参数里可用。
- 复核通知只到「追加事件」，任务自动推进与 resume 仍属 INT-09。
