- 本次目标、原问题及源码依据：
  - 目标：让"能不能用某个数据集/模型/记录"在两套代码里只有一个答案——B 的资源索引与 C 的业务行对同一对象给出**同一个归属、同一个项目、同一个版本**；原页面与 Agent 共用同一套判断。
  - 原问题（逐条按源码确认）：
    1. `agent/policy_bridge.py:_resolve` 只查 `agent_resource`；C 新建的数据集/模型/记录从未登记，业务库里有、索引里没有 → `resolve_resource` 直接返回 `None` → 工具报"资源不存在"。也就是说 INT-02 之后工具**能列出来但用不了真实资源**。
    2. `agent/permissions.py:register_resource` 命中已有来源时 `return _resource_view(existing)`，**没有做可见性判断**：另一个用户可以借"幂等返回"读到别人资源的项目、名称、版本。
    3. `agent/routes.py:register_resource` 直接接受请求体里的 `source_table`/`source_id`，任何人都能把任意业务行认领进自己项目。
    4. `agent/legacy.py` 的迁移只在手动调用时执行，应用启动路径没有接上；"哪些资源对登录用户只读开放"没有可核对的清单。
    5. `agent/policy_bridge.py:project_file_access` 只允许项目归属人，管理员与系统默认项目都无法按策略工作；C 的上传/预览/下载全部读这一项。
    6. C `routes/dataset.py` 有 14 个、`routes/model.py` 有 10 个路由挂 `admin_required`：普通用户完全不可用，管理员可操作任意人的资源，两个方向都不对；`list_datasets`/`list_models` 由管理员改为登录用户后会列出所有人的资源。
    7. C `services/tool_handlers.py:704` 在模型与图片 `project_id` 不等时硬阻断（`MODEL_PROJECT_MISMATCH`），导致默认只读模型与非同项目的本人资源都无法用于检测。

- 为何这样改、复用了哪些现有实现：
  - 归属登记放在 B 侧新模块而不是改 C 的业务服务：C 的 handlers/services 不感知 `agent_resource`，B 在 `execute` 返回后按 `business_refs` 登记，业务代码零改动，也避免"业务失败但登记成功"。
  - 数据集/模型归属优先取上传件链路：`file_assets` 是唯一同时带 `owner_id` 与 `project_id` 的真实来源，比"猜创建人"可靠；`datasets`/`models` 表没有 user_id，这一点在 8.1 对照表里是显式的。
  - `agent_registration_failure` 独立成表而不是塞进事件流：登记失败需要**可查询、可重试、可销账**，不是一条给前端看的消息。
  - 页面授权与 Agent 共用 `resources.access_check`：两套判断如果分开写，迟早会出现"页面能传、Agent 不能"或反过来。
  - `C` 的路由只换装饰器、不删检查：`resources_required` 支持一请求多资源（父子模型比较），列表仍走 SQL 过滤而不是先全查再筛。
