## 1. 个人复核客户端（11.2 前四项）

新增 `services/personal_review_client.py`：

- `PersonalReviewClient(gateway)`：把本人连接适配成旧复核服务要的协议
  `review_detection_structured(image_bytes, detections, *, class_names, secondary_image_bytes, secondary_modality)`，
  以及 `health_check()`。凭据只来自 `agent.connections.model_client(actor)`，**没有第二份 Key**。
- `create_personal_review_client(actor, verify_vision=True)`：先取本人连接，再 `require_capability(actor, "vision")`。
  未配置 → `MODEL_NOT_CONFIGURED`；连接在但「看图」能力未验证/不支持 → `MODEL_CAPABILITY_MISSING`。
  两者都是**阻断**，不回落。
- 提示词里带 YOLO 结果、数据集真实类别表、以及「本记录只有 RGB / 第二张图是某模态配图」的说明。
  有多模态图时把两张 `image_url` 一起发；没有就只发一张。

接线：

| 入口 | 之前 | 现在 |
|---|---|---|
| `POST /records/<id>/ai-review` | `LLMVLClient()`（全局 Key） | `create_personal_review_client(load_actor(g.user_id))` |
| `POST /records/ai-review/batch` | `client_factory=LLMVLClient` | 零参数闭包 `_personal_review_client` |
| `GET /llm/health` | `check_vl_health(LLMVLClient())` | 同上 |
| Agent `review.ai` | `client_factory=adapter.model_client_factory`（返回的是聊天网关，没有复核方法） | 装配层注入 `review_client_factory`（`_personal_review_factory()`，含能力校验）；未注入时把网关包一层 `PersonalReviewClient`，已实现协议的客户端不会被二次包装 |

`BusinessToolAdapter` 新增 `review_client_factory` 依赖槽，`review.ai` 的可用性判定接受任一工厂；
`agent/bootstrap.py` 注入 `_personal_review_factory()`。

## 2. 按真实记录取图（11.1.4）

`ai_review_service.review_detection` 的查询扩到一条 SQL 拿全：

```sql
SELECT r.id, r.original_image_bucket/key, r.secondary_image_bucket/key, r.detection_result,
       m.model_mode, m.secondary_modality, d.structure_info
FROM detection_records r LEFT JOIN models m ... LEFT JOIN datasets d ...
WHERE r.id = ?
```

- 有 `secondary_image_bucket/key` → 真的取第二模态图并发出去；
- `model_mode = multimodal` 但没有第二模态图 → 抛 `AIReviewInputError`（新增），**不发请求、不写结论**，明确说"缺少 X 配图"，不拿 RGB 或增强图冒充；
- 类别表来自 `datasets.structure_info`（`utils.dataset_classes.dataset_class_names`），随提示词一起下发；读不到只影响提示词，不阻断。

## 3. 解析失败不重复计费（11.1.5）

删掉 `for attempt in (1, 2)`。现在：上游异常 → 写 `needs_human_review` 兜底结论 + 抛 `AIReviewUpstreamError`；格式错误 → 写兜底 + 抛 `AIReviewParseError`。**每个记录只发一次远端请求**，日志里不再有 `attempt=`，用户要重试就再点一次（等于新建一次动作）。

同时把对外文案彻底分开：

- `AIReviewUpstreamError(message="", *, public_message=None)`：位置参数只是内部原因，**不会**变成对外文案；`public_message` 缺省为通用提示，401 时显式传"检查 Key 与服务商地址"。
- 批量汇总用 `public_message`，所以 `provider detail must stay private` 这类内容再不会出现在 `items[].error`。

## 4. 逐项状态（11.2 最后一项）

`review.ai` 的 outputs 新增 `status`：全失败 `failed`、部分失败 `partial_failed`、全成功 `succeeded`；
`failed` 计数始终存在，外层 Operation 即使是 succeeded 也掩盖不了逐项失败。

## 5. 顺手修的两个真实缺陷

- `feedback_dataset_service.add_confirmed_record` 改成 `SELECT *` + 列存在性判断：老库没有 `structure_info` 时按"无类别表"处理。
- `review_service._validate_annotations(annotations, class_names=None)`：没有真实类别表时**不再拿默认类别表去猜**（原来会拿 `YOLO_CLASSES_CONFIG` 当默认，导致"crack 未知类别"），只校验几何与结构。

## 7. 未做与风险

- `/records/<id>/analyze` 与 `/generate-suggestions` 两个旧接口仍在用 `LLMVLClient()`（全局 Key）。它们不在 INT-06 关键词点名的三处（单条/批量/health）内，但违反"同一账号同一连接"，建议下一轮一起收口。
- `PersonalReviewClient.health_check` 只查认证与模型可见性；真正的"能否看图"仍由 `probe_vision` 负责，二者不要混为一谈。
- 能力校验要求连接上已有 `vision=ok` 的检查结果；新用户第一次复核前必须先跑一次能力检查，否则会收到"尚未验证"的提示（这是有意的阻断）。
- 未接真实 DeepSeek Key 做过端到端双图调用；本轮只验证了消息装配（两张不同 `image_url` + 类别表 + 检测结果）与错误路径。
